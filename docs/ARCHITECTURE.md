# 架构

## 三层职责

1. `.engine/stick-steel/lib/duel/physics.ts` 及 rig：由固定的上游源码和可审计补丁生成。Rapier 120 Hz，身体执行、动作和接触伤害属于游戏。
2. `src/arena/runtime.ts` 的步骤执行：根据步骤时长/接受反馈/超时产生连续 move、aim 和一次性命令。`aim_to` 产生有界目标，不移动刚体、不保证命中。
3. 同文件的条件选择：从只读公开观察计算特征，按规则优先级、冷却与历史事件选招式，不读取对手内部资源。

`src/engine/adapter.ts` 是受信边界。先取得两个观察，再计算两个动作；双方动作结构均通过校验后，才写入任何一方输入。其外部控制与联机无关。`src/arena/match.ts` 每6个物理步调用双方策略，保存结果与每4步的实际姿态。

`src/viewer/stage.ts` 复用原 avatar / weapon-view / camera / effects / audio 模块。网页驱动物理按固定步进追赶墙钟，落后时显示欠账，不丢物理步。页面隐藏或用户暂停属于本机开发暂停，不是严格实时服务器。CLI 同内核不等待墙钟，方便试战。

回放创建单独的展示世界，通过上游快照消费者放置历史姿态，绝不再运行裁判；不能把回放对象重新作为正式比赛继续模拟。现阶段回放30Hz采样，不含完整保存/恢复所有约束的能力。

## 冻结与身份

`prepare-engine.mjs` 校验全部上游原始文件，生成外部控制补丁后的副本，再为规则、适配器、执行器、Match、依赖锁和补丁建立摘要。网页生成只读双设计快照；CLI 会话和冻结副本另有原配置 SHA-256。正文、外观和开发样例不属于引擎身份。

本地 elapsed 时间和文件系统不可冒充防篡改计时。当前只接收声明式配置；没有未受信任子进程或云安全沙箱承诺。

## 上游保留与边界

只有一个游戏物理内核，不移植旧 MuJoCo/自研轻量内核。上游模块和测试以原始字节保存；未使用的商店/联机模块不进入新入口的依赖图。源码保留不表示平台使用生产服务。

原游戏自动朝向、身体平衡和握持辅助对双方统一开放。当前仅练习场单手剑。接触处理顺序及同 tick 双重失能等边界仍需专门审计，不把双方参数一致夸大成全面公平性证明。
